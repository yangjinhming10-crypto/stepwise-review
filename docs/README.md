# stepwise-review —— 功能与使用文档

> **skill 位置**：本仓库根目录 `SKILL.md`
> **当前版本**：v1.1（2026-09-01，串行效率四项优化，双路独立审查零阻断通过；v1.0 曾经三路验收通过）
> **维护规则**：任何对 SKILL.md 的修改必须同步更新本文档与 `CHANGELOG.md`。

## 一、这是什么

`/stepwise-review` 是一个**手动触发**的执行工作流 skill：你提出需求，它把需求拆成带验收
标准的步骤；每一步的实现在一个新开的**实现子代理**里完成，再由另一个全新的**独立审查
子代理**对照验收标准审查，通过才进入下一步；最后由独立**终审**对照原始需求整体把关。

解决的核心问题：单对话里"自己写自己审"会自我合理化——独立上下文的审查者只看需求、
标准和 diff，才会真挑刺。

核心不变量：**主对话只做编排**——不亲自实现、不亲自审查；质量住在审查者的独立复验里。

## 二、功能特性（按流程走读）

### 1. 拆步（§1）
需求 → 步骤清单 + **依赖图**：互不依赖的兄弟步骤显式标注"可并行槽"，依赖存疑按
有依赖处理。每步含改动范围 + 可判定的验收标准（"基本完成"这类措辞不合格）。
反假拆（不为凑数拆假步骤）、反假合并（不为凑轻量资格把多步压成一大步）。

### 2. 模式判定（§1a）
- **轻量模式**：三条件全满足才自动建议——单步、改动范围小（通常 ≤2 个文件、无跨模块
  契约变更）、验收标准可判定。省计划审查与终审，**保底**实现者 + 独立审查者双关卡。
- **完整模式**：其余一切情况，全关卡一个不少。
- 判定结果并入确认消息，用户一个词可否决；否决或 `--full` → 回退先过计划审查。
- 轻量执行中发现实际是多步/高风险 → 停止升级，建议转完整模式（已过审产出保留为基线）。

### 3. 计划审查（§1b，完整模式）
全新只读子代理按五条审计划：覆盖完整性、顺序与依赖、原子性与边界（含并行候选的
"零交集且语义独立"判定）、验收标准可判定性、范围纪律。修订后复审，两轮仍有未解决
发现即升级用户。

### 4. 用户确认（§1c）
步骤清单 + 模式判定 + 计划审查结论一次呈报；git 仓库附问"是否允许每步任务域 commit"
（`--commit` 可预设）。这是唯一必经的人工闸门。

### 5. 逐步执行（§2）
- **基线三模式**：git+允许提交（任务域 commit，放弃仅 revert 该提交，冲突即停升级）；
  git+不允许提交（步前快照到 `tmp/stepwise-review/`，放弃/升级从快照恢复）；
  非 git（快照模式，含越界处置与 ignore 确认）。
- **验证命令登记表**：登记每步可复现命令（标注对应的验收标准与副作用）与**实际
  影响符号集**，累积回归按符号交集选命令（重跑量不随步数线性增长）；与实现者
  摘要、判定表一并落盘，支持中断恢复与在途接续。
- **并行条件**（严格）：候选限拆步标注的**可并行槽**，且需独立工作区隔离（git
  worktree）+ 零交集 + **契约抽验通过**（耦合边界跑可执行验证，证据背书而非
  主观判定）+ 允许提交；本步审查不过立即暂停后续（含隔离区）；合回后照常审查。
- **审查窗口预热**：某步审查期间，下一步实现者只读侦察并产出**不落盘**的实施
  计划——打回则作废、通过则并入上下文包，把探索成本从写盘阶段挪进等待窗口。
- **实现子代理（2a）**：上下文包在派发时现做（路径、行号线索、命令原文、规范摘录），
  免冷启动；返回改动说明、全部触碰文件、验证命令与输出。
- **独立审查子代理（2b）**：全新对话、不给实现者自评；输出**判定表**（通过/不通过/
  未验证 + 证据，命令必须亲自重跑）；证伪姿态；定向阅读 + 引用链追溯；并行验证 +
  防缓存假绿；符号交集累积回归；未能验证项显式呈报；只报告不改源文件（验证产生
  的缓存/产物豁免）。
- **打回闭环（2c）**：判定表无"不通过"且三类发现（缺失/越界/实现错误）为空才过关；
  不过则定向打回同一实现者做最小修复，重开新审查者复审；两轮上限后升级用户。
- **中途 re-plan（2e）**：审查暴露计划缺陷或用户变更需求 → 暂停 → 修订 → 增量过 1b →
  用户确认 → 继续；可插入针对已完成产出的修复步骤。

### 6. 独立终审（§3，完整模式）
终审者只拿原始需求 + 累计改动 + 各步验收标准 + 登记表（**不给**逐步审查结论，防锚定），
判整体完整性、跨步骤一致性、接口自洽；发现必须闭环处置（发回责任实现者修复 →
新子代理复审 + **全量重跑登记表**做全局回归）。

### 7. 红线（七条）
控制器不实现不审查；不复用实现者/前序审查者的对话或结论；计划未经审查与确认不执行
（轻量例外）；审查未过不放行产出、不省终审（轻量例外）；终审发现必闭环；未能验证项
不得默默计为通过；两轮上限后必须升级。

## 三、使用方法

### 调用形式

```text
/stepwise-review <需求或任务描述>
/stepwise-review --focus "性能与内存" <需求>
/stepwise-review --commit yes <需求>
/stepwise-review --light | --full <需求>
```

| 参数 | 作用 |
|---|---|
| `--focus "风险面"` | 把关注面注入所有审查子代理（追加项，不替代基础检查） |
| `--commit yes/no` | 预设基线模式，免掉确认时的提问 |
| `--light` | 强制轻量（不满足单步硬条件时忽略并告知） |
| `--full` | 强制完整模式 |

### 你需要交互的时点（很少）
1. **确认步骤清单**——一次消息包含：清单、模式建议（可否决）、计划审查结论、
   commit 问题；
2. **升级时**——某步两轮审查不过 / 需求矛盾 / 轻量任务暴露高风险；
3. **收最终报告**——每步判定表与修复记录、未验证项汇总、终审结论、产出位置。

### 适用 / 不适用
- **适合**：多步骤功能开发、带复现命令的 bug 修复、重构（回归风险高）、不熟代码库的
  重要改动、要求 diff 干净的场景、可判定验收标准的文档/调研任务；单步小改动会自动
  建议轻量模式。
- **不适合**：探索性 spike（需求在漂移）、纯问答分析（无改动可审）。本 skill 纯手动
  触发，不用即不介入。

### 成本预期
完整模式约为普通执行的 2–3 倍（每任务 4+ 个子代理）；轻量模式子代理数约一半。
效率机制（定向阅读、并行验证、登记表、定向打回、受限并行）在不减关卡的前提下压缩
墙上时间，典型任务可省 30–50%。
